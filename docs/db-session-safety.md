# DB / Session Safety Guide

이 문서는 이 프로젝트를 이후에 수정하는 사람이나 다른 에이전트가
사용자 학습 데이터를 날리지 않고 패치할 수 있도록 만든 운영 기준 문서다.

## 현재 운영 구조

- 배포: Vercel
- DB: Neon Postgres
- 원격 저장 활성화 기준: `DATABASE_URL` 환경 변수 존재
- 사용자 식별: `닉네임 + 서버 세션 쿠키`
- 프런트 저장:
  - 원격 저장 사용 시: DB + 세션 쿠키
  - 원격 저장 미사용 시: 브라우저 localStorage

## 현재 핵심 테이블

- `study_users`
  - 사용자 닉네임과 학습 진행도 저장
- `study_sessions`
  - 로그인 세션 저장

현재 앱에서 사용자 진행도는 `study_users.progress_json`에 저장된다.

## 절대 하면 안 되는 것

- `study_users` 테이블 삭제
- `study_sessions` 테이블 삭제
- `study_users.progress_json` 컬럼 삭제
- 기존 `nickname_key` 규칙을 사전 마이그레이션 없이 변경
- Vercel의 `DATABASE_URL`을 다른 DB로 무심코 교체
- 테스트용 초기화 쿼리를 운영 DB에 실행

위 항목 중 하나라도 잘못 건드리면 기존 사용자의 학습 데이터가 끊기거나 사라질 수 있다.

## 안전한 패치 원칙

1. 가능한 한 additive change만 한다.
2. 컬럼이 필요하면 추가하고, 기존 컬럼은 바로 삭제하지 않는다.
3. `progress_json` 구조를 바꿀 때는 기존 데이터도 읽히게 유지한다.
4. 세션 구조를 바꿔도 `study_users`의 사용자 데이터는 그대로 유지한다.
5. 로그인 방식이 바뀌어도 기존 닉네임 사용자의 매핑 경로를 남긴다.

## progress_json 변경 규칙

가장 중요한 원칙은 하위 호환이다.

- 새 필드는 추가 가능
- 기존 필드는 당장 삭제하지 말 것
- 프런트 `sanitizeProgress(...)`에서 이전 구조를 복원 가능하게 유지할 것
- 값이 없을 때 기본값으로 복구되도록 할 것

예:

- 안전: 새 통계 필드 추가
- 위험: 기존 필드명을 바꾸고 변환 로직 없이 바로 배포

## 세션 변경 시 규칙

현재 세션은 서버 쿠키 기반이다.

세션 로직을 바꾸더라도 아래 원칙은 유지해야 한다.

1. 사용자 본체 데이터는 `study_users`에 남겨둘 것
2. 세션은 언제든 재발급 가능하게 설계할 것
3. 세션 테이블을 초기화해도 사용자 진행도는 복구 가능해야 할 것
4. 로그인 규칙이 바뀌면 기존 닉네임 사용자의 진도를 연결하는 마이그레이션 경로를 둘 것

즉, 세션은 버려져도 되지만 사용자 학습 데이터는 버려지면 안 된다.

## 닉네임 정책 변경 시 주의점

현재는 닉네임 정규화 후 `nickname_key`로 사용자 계정을 식별한다.

이 규칙을 바꾸면:

- 기존 사용자가 다른 사람으로 인식될 수 있음
- 같은 사람이 새 계정으로 분리될 수 있음
- 기존 진행도가 보이지 않을 수 있음

따라서 닉네임 규칙을 바꿀 때는 반드시:

1. 기존 `nickname_key` 데이터를 어떻게 이전할지 정의
2. 운영 DB에서 변환 쿼리 또는 호환 코드 준비
3. 배포 전에 테스트 데이터로 검증

## 배포 전 체크리스트

배포 전에 아래를 확인한다.

1. `npm run lint`
2. `npm run build`
3. DB 관련 파일 변경 여부 확인
4. 세션 관련 API 변경 여부 확인
5. `progress_json` 구조 변경 여부 확인
6. 삭제성 SQL 또는 destructive migration이 없는지 확인
7. Vercel 환경 변수 `DATABASE_URL`이 운영 DB를 그대로 가리키는지 확인

## DB 관련 파일을 수정했다면

다음 파일을 특히 주의해서 본다.

- `api/_lib/db.js`
- `api/_lib/auth.js`
- `api/auth/login.js`
- `api/auth/me.js`
- `api/auth/logout.js`
- `api/progress.js`
- `src/lib/remoteProgress.ts`
- `src/App.tsx`

이 파일들은 로그인, 세션, 진행도 저장 흐름에 직접 연결된다.

## 안전한 변경 예시

- UI만 수정
- 레슨/문제/콘텐츠 추가
- XP 계산 방식 조정
- 새 통계 필드 추가
- 설정 화면 추가
- 세션 만료 시간 조정

## 위험한 변경 예시

- `study_users`를 다른 테이블로 교체
- `progress_json` 구조를 통째로 새 포맷으로 변경
- 닉네임 키 생성 규칙 변경
- 세션 쿠키 이름/전략 변경 후 기존 사용자 복구 경로 미구현
- 새 DB로 갈아끼우고 기존 데이터 이전 없음

## 다른 에이전트를 위한 작업 원칙

이 프로젝트를 수정하는 에이전트는 아래를 기본 규칙으로 삼는다.

1. 사용자 데이터는 코드보다 중요하다.
2. 로그인 방식보다 진행도 보존이 우선이다.
3. 구조를 바꿀 때는 이전 데이터가 그대로 읽히는지 먼저 본다.
4. 확신이 없으면 테이블 삭제 대신 문서화 후 보류한다.
5. 운영 DB 구조를 바꾸는 작업은 설명 없이 밀어붙이지 않는다.

## 문제 발생 시 우선 확인할 것

사용자가 "진도가 사라졌다"고 하면 먼저 아래 순서로 본다.

1. `DATABASE_URL`이 바뀌지 않았는지
2. 배포가 다른 Vercel 프로젝트로 나간 건 아닌지
3. 닉네임 정규화 규칙이 바뀌었는지
4. 세션 쿠키만 끊긴 것인지
5. `study_users.progress_json`에 실제 데이터가 남아 있는지

세션이 끊긴 것과 데이터가 삭제된 것은 다르다.
먼저 "로그인 연결 문제"인지 "실제 데이터 손실"인지 분리해서 본다.

## 권장 운영 습관

- 큰 배포 전에는 Neon 브랜치/백업 확인
- 스키마 변경 전에는 테스트 브랜치 DB에서 먼저 검증
- 운영 중에는 destructive migration 금지
- 문서 없이 로그인 구조를 바꾸지 말 것

## 한 줄 원칙

세션은 바뀌어도 괜찮지만, 사용자의 `study_users.progress_json`은 깨지면 안 된다.
